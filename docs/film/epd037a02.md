# EPD037A02 同屏刷新与校色

目标为实物排线 **HINK-T037A02-A1 / EPD037A02**、驱动IC **JD7601**。原生720×480，观看480×720竖屏、排线下、标记左上。GDEH037E01是佳显料号，只作交叉参考，不直接混用校色参数。

## 已有依据

[OSPTEK原厂资料](https://github.com/osptek/epd-3.7-480x720-spi-jd7601/tree/main/versions/EPD037A02)给出六色、32pin、JD7601与2MHz示例；示例时钟不是最大频率证明。PDF有TBD及BUSY说明矛盾，需结合源码和本机日志。[佳显资料](https://www.good-display.com/product/991.html)机械图与函数的IC命名不一致，关闭的water-ripple分支不证明47fps。

用户提供的[同型号项目](https://oshwhub.com/sila/project_mspomzec)截图描述64码及512/4096码扩展，尚未取得附件源码；不据此承诺有效色数。已保存epd-color-lab核心快照的9份波形与当前Ark相同。

## 本轮工具

[串口诊断](../../tools/epd-profile/README.md)由默认关闭的 CONFIG_ARK_EPD_PROFILE 启用，记录MonoFast/ColorFast/ColorQual的INIT、LUT、RAM、REF、PON、POF及总耗时。SPI错误、BUSY超时或忽略BUSY的调用不计成功。

[同屏测试生成器](../../tools/epd-panel-lab/README.md)输出两种彩色各两页32码色卡、12帧Mono基准、PNG和manifest。全部0..63直接入文件，不经RGB重新量化；预览只是当前Web RGB估计。本轮不修改LUT、PLL、电压、40MHz SPI或刷新延时，不新增编码格式。显示版本保持3.2.5。

## 实测顺序

1. 记录ELF指纹、排线型号、温度、此前画面和文件列表。用独立文件名，不覆盖用户图片。
2. 通过现有网页上传，核对回包及文件列表。单帧归film，多帧归animation；先确认方向、完整显示和无错位。
3. 播放Mono基准，分开记录首次准备帧、同一保持上电会话的稳态帧。停止后的POF不归上一帧；不把预热结果当冷启动，也不把重复画面与黑白翻转当相同负载。
4. 固定顺序显示Qual/Fast色卡，等待完成并记前一画面和模式。取样避开字、边框和X。照片只能定性对比；准确RGB/Lab校色需受控照明和测量设备。
5. 用 python tools/epd-profile/summarize.py capture.log --json 汇总。空日志、截断记录和失败样本保持失败/缺失，不填0冒充实测。

## 判定边界

Mono源图43200B展开成172800B全屏传输。40MHz线速至少34.56ms，47fps预算21.28ms，当前路径不满足47次完整更新/秒。这是传输下界，不是实测帧率；RAM含编码/SPI事务/BUSY，REF含命令/BUSY/固定延时。历史410ms/帧和3.35s首帧只作历史记录。

分段结果再决定是否优化批量SPI、同LUT免重载或调度。未知轻量传输、窗口命令、PLL映射须有同控制器依据再验证。分别记录编码数、候选数、不同RGB数、实屏可分辨色数，不以512/4096编码代替有效色测试。通行证继续ColorFast快刷，Film保留ColorQual和已有实测色板。

## 2026-10-26 参数修复与25fps目标分析

用户将目标限定为：允许降低《Bad Apple!!》视频分辨率，但要求实体画面至少25fps。25fps预算40ms，不能以文件的帧率标记、完成回包或函数调用数代替可辨别的有效显示帧率。用户视频短链 https://b23.tv/RYeFfWu 本次访问返回HTTP412，未下载或转换视频；以下不假定该资源的实际分辨率、时长和编码。

### 先修复冷启动参数查询

BLE GET路由原先直接调用owner->on_param_get，未载入的动画RAM状态会返回frame_ms=0。现在统一走已有app_manager_param_get，按原NVS槽载入或套默认值后再回包。0x46/0x48/0x4A共用该路径；SET、参数结构、state_ver、NVS布局和已保存值均不变。检查脚本 tools/epd-profile/check_app_param_get.py 编译实际C路由及load/save函数，验证冷/重复GET、无保存/进入app、冷/重复SET和默认值回落；NVS/BLE/参数回调是接口fixture，不等于硬件验证。

### 当前三个独立限制

1. 当前Mono是全屏差分：1bpp输入43200B，但每次向DTM1写172800B。未变化像素使用差分码，不等于硬件窗口传输。原注释的“JD7601无窗口命令”没有公开寄存器手册支撑；准确边界应是当前路径未实现窗口，尚未取得本屏可用窗口命令依据。
2. 当前同屏BUSY低宽约121.2ms。即使软件编码和传输耗时全消失，沿用此单周期也不能达到40ms；保持全屏串行写入和同波形时，线速34.56ms+BUSY121.2ms的理想下界约155.76ms，即约6.42次/秒，尚未计入恢复等待、事务和其它开销。这是条件计算，不是已达到的帧率，也不是本屏换模式后的绝对上限。
3. 动画参数最小100ms，当前app用100ms tick累计并由FRAME_DONE接续；即使将来面板快过40ms，也需另行改为准确的帧期限调度，并同步参数范围及设置候选。单独把数值改为40不能解决前两项，本轮未提前扩展这些接口。

### 下一次实验所缺的具体资料

向屏幕厂商索取时应明确以下信息，而不只索取模组规格书：

> 实物为HINK-T037A02-A1 / EPD037A02，3.7寸480×720六色，JD7601。现有自定义黑白MonoFast每次REF后BUSY低电平约121ms，目标研究更短黑白更新。请提供JD7601 command table及waveform/LUT format：0x20的799字节字段布局、时间单位、重复计数、结束/跳过条件；是否存在适用于该面板的更短黑白参考LUT；是否支持gate/source扫描起止或扫描行数限制，其命令、合法范围、RAM写入步进及BUSY完成条件分别是什么？若JD7601/IST7601为不同标记或修订，也请说明本FPC适用的IC版本。

取得明确候选后沿用同一四帧基准，逐项改变波形时间或已定义扫描范围，保留REF→BUSY断言/释放→原尾部等待；分别记录RAM、BUSY、REF和帧间隔，并核对连续运动与区域外保持。随后再测Bad Apple。短写DTM1或裁剪视频本身不算缩短硬件扫描；本轮没有确认25fps能力。
